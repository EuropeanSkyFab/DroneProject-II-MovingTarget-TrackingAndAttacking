# P2 模式策略契约（纯 Python 层）

## 1. P2 到底做什么

可以把 P2 想成一个“交通规则调度员”：

- P1 会算几何点（目标在哪、拦截点在哪）。
- P2 决定**这一帧到底该不该发点**，以及**哪个动作该用哪个速度**。
- ROS 适配节点（`algorithm_node.py`）只负责把 P2 的结果变成消息。

P2 不订阅话题、不发布、不打日志、不生成 `stamp`，所以可以用 pytest
直接测，不需要启动 ROS。

### 1.1 从 P1 到 P2 发生了什么

P1 是“三个几何计算函数”，P2 是“一帧该不该发点、为什么”的决策层：

| 维度 | P1 | P2 |
| --- | --- | --- |
| 入口 | 调用者分别调 `predict_target` / `solve_intercept` / `apply_constraints` | 统一调 `plan(raw_action, own, target, params)` |
| 输出 | 点或 `None` | `PlanResult`，带动作、原因、是否可达、是否裁剪 |
| 动作 | 只区分 TRACK / INTERCEPT / ATTACK | 7 个动作 + 未知动作拒绝 |
| 目标年龄 | 只有 P1 的 `max_age` | 再加 P2 的 `max_pred_age`（默认 0.5s） |
| 速度 | 调用者传一个 `v_max` | `PlanParams` 按动作选 7.6 / 12.4，`v_max` 兜底 |
| ATTACK 无解 | 返回 `None`，语义靠调用者猜 | 明确 `attack_no_solution`，适配层再发保持点 |
| 未知动作 | 可能被调用者当成 HOVER | 明确拒绝，不改变当前模式 |
| 测试 | 单函数单测 | 参数、策略、模式切换回放三层测试 |

关键变化不是“算法公式变了”，而是**把散落在调用者里的判断收进一个可测试的
契约层**：什么动作发点、什么情况不发、失败原因是什么，都由 `plan()` 统一
回答。

涉及文件：

| 文件 | 作用 |
| --- | --- |
| `src/algorithm_pkg/algorithm_pkg/plan_types.py` | `PlanResult`、动作分组 |
| `src/algorithm_pkg/algorithm_pkg/plan_params.py` | `PlanParams`，按动作选速度 |
| `src/algorithm_pkg/algorithm_pkg/plan_policy.py` | `plan()`，一帧策略入口 |
| `src/algorithm_pkg/test/test_plan_params.py` | 参数校验测试 |
| `src/algorithm_pkg/test/test_plan_policy.py` | 7 动作、无效输入测试 |
| `src/algorithm_pkg/test/test_plan_replay.py` | 连续切换动作测试 |

## 2. 七个动作分别怎么处理

| 动作 | P2 是否发点 | 发什么 | 原因字符串 |
| --- | --- | --- | --- |
| `TRACK` | 是 | 目标预测点，不做 standoff | `track_target_point` |
| `INTERCEPT` | 能解就发；不能解发尾随点 | 最早拦截点，或目标后方 `d_tail` 米 | `intercept_point` / `fallback_tail` |
| `ATTACK` | 能解才发；不能解不发 | 最早拦截点，**绝不尾随** | `intercept_point` / `attack_no_solution` |
| `TAKEOFF` | 否 | 中枢自己生成 | `takeoff_center_generated` |
| `HOVER` | 否 | 中枢自己生成 | `hover_center_generated` |
| `RETURN` | 否 | 中枢自己生成 | `return_center_generated` |
| `RESUME_PATROL` | 否 | 目前没有行为定义 | `resume_patrol_unspecified` |

补充：

- 未知动作（拼错、`None`、空串、纯空格）一律不发点，原因
  `unknown_action`；**不会自动改成 HOVER**，否则一个拼写错误就会让
  飞机继续按旧模式飞。
- `TRACK` 只需要目标位置，所以只有一帧、`velocity_valid=False` 时
  仍然可以发点。
- `INTERCEPT`/`ATTACK` 需要目标速度；`velocity_valid=False` 时
  不发点，原因 `velocity_unavailable`。单帧速度是按 0 处理的，
  不是真的“目标静止”。

## 3. `plan()` 的检查顺序

固定顺序，方便复现和排查：

```text
1. 归一化动作（strip + upper）
2. 未知动作？ -> unknown_action
3. 中枢动作？ -> *_center_generated
4. RESUME_PATROL？ -> resume_patrol_unspecified
5. target 是 None？ -> target_missing
6. target.valid 是 False？ -> target_invalid
7. target.age > max_pred_age？ -> target_too_old
8. own 不是有限三维点？ -> own_invalid
9. INTERCEPT/ATTACK 且 velocity_valid=False？ -> velocity_unavailable
10. solve_intercept()；无点则返回具体原因
11. apply_constraints()；仍无点则 constraint_rejected
12. 返回 PlanResult
```

注意第 7 步：P1 的 `valid` 只代表“在 P1 的 `max_age` 内”；
P2 又加了 `max_pred_age`（默认 0.5 秒），两者都要满足。

## 4. `PlanParams`：参数集中管理

```python
PlanParams(
    v_max=6.0,             # 兜底
    v_max_intercept=7.6,   # 0.38 m × 20 Hz
    v_max_attack=12.4,     # 0.62 m × 20 Hz
    t_go_max=8.0,
    min_distance=0.5,
    d_tail=4.0,
    min_alt=3.0,
    safe_alt=5.0,
    max_alt=50.0,
    max_xy=1000.0,
    max_step=None,
    max_pred_age=0.5,
)
```

要点：

- 三个速度不要合成一个。`v_max_for("INTERCEPT")` 返回 7.6，
  `v_max_for("ATTACK")` 返回 12.4，其他动作返回 6.0。
- 7.6/12.4 来自**飞控控制周期 20Hz**，不是规划节点的发布频率；
  飞控周期变了就改参数，不要在策略代码里写死。
- 构造 `PlanParams` 时会校验非法值（0、负数、高度矛盾等），
  让配置错误在启动时暴露，而不是飞到一半才出问题。

## 5. `PlanResult`：不要用裸 `None` 表示“不发点”

```python
PlanResult(
    action="ATTACK",
    raw_action="attack",
    point=None,
    reachable=False,
    t_go=None,
    reason="attack_no_solution",
    clipped=False,
)
```

| 字段 | 含义 |
| --- | --- |
| `action` | 归一化后的动作 |
| `raw_action` | 上游原始值，便于查大小写/空格 |
| `point` | 要发布的 ENU 点；`None` 表示不发 |
| `reachable` | 是否真正可达；尾随点是 `False` 但仍会发 |
| `t_go` | 预计拦截时间；TRACK/尾随点为 `None` |
| `reason` | 机器可读原因，日志直接打印 |
| `clipped` | 点是否被安全边界裁过 |

发布规则只有一句：

```python
if result.point is not None:
    发布 /planning/target_pose
```

注意：`reachable=False` 不等于不发。`INTERCEPT` 的尾随点就是
`reachable=False`，但它是合法的兜底点，应该发；`ATTACK` 无解时
`point=None`，才是不发。

## 6. 和 ROS 适配层 / 中枢的边界

- P2 不管 `/planning/target_pose` 的 JSON、不管 `stamp`。适配层发布时
  使用**发布时刻**的 ROS 时钟秒数，不能用目标消息的旧时间戳。
- 规划 JSON 里的 `action` 目前不是中枢的控制输入；中枢的模式和限幅
  来自 `/strategy/cmd`。P2 的 `action` 主要用于选速度、写日志和未来
  扩展，不能假设中枢会因为它改变行为。
- `RESUME_PATROL` 在中枢和接口里都没有定义，P2 明确返回
  `resume_patrol_unspecified`，不猜坐标。
- P2 本身不解决“中枢保留上一帧 ATTACK 点最多 2 秒”的问题；适配层
  `algorithm_node.py` 在 `ATTACK` 无解或目标失效时，会发布“己方当前位置
  保持点”（高度按 `min_alt` 收进边界）。P2 仍然只返回“不发点”，
  不会伪造 ATTACK 尾随点。

## 7. 测试怎么读

```bash
PYTHONPATH=src/algorithm_pkg /usr/bin/python3 -m pytest -q \
    src/algorithm_pkg/test
```

成功时终端末尾会打印“算法实测结果”，每条测试按“场景 / 预期 / 实测”
三行说明：

- **场景**：测试函数 docstring 中的“场景”段，说明在什么战术情形下测试；
- **预期**：docstring 中的“预期”段，说明期望的结果和边界；
- **实测**：`measured()` 记录的实际数值，说明这次运行真实测出了什么。

例如：

```text
- test_attack_unreachable_does_not_return_tail_point
  场景：ATTACK 目标更快，直线追不上。
  预期：point=None，reason=attack_no_solution；不能退化成尾随点。
  实测：point=None, reason=attack_no_solution
- test_intercept_unreachable_returns_tail_point
  场景：INTERCEPT 追不上，允许退化为尾随点。
  预期：point=(6,0,10)，reachable=False，reason=fallback_tail。
  实测：point=(6.000, 0.000, 10.000), reachable=False, reason=fallback_tail
```

这样不需要翻测试源码，也能知道每条测试在验证什么。

P2 测试分三组：

1. `test_plan_params.py`：默认参数、按动作选速度、非法参数。
2. `test_plan_policy.py`：7 个动作、未知动作、目标/己方无效、
   速度无效、ATTACK 不尾随、INTERCEPT 尾随、边界裁剪。
3. `test_plan_replay.py`：连续切换动作，确认不会把上一模式的点带过来。

## 8. 当前不包含什么

P2 只做纯策略；ROS 适配层已经调用 `plan()`，但 P2 本身不包含：

- ROS 消息、发布、日志和参数声明（在 `algorithm_node.py`）；
- `PlanResult` 到 JSON 的序列化；
- 中枢 `latest_plan_targets` 的 2 秒保留问题（适配层用保持点兜底，
  不是 P2 的职责）；
- E/F 同 topic 自回灌问题；
- 飞控真正的加速度/转弯半径限制。

这些放在 P4 联调和 P2 之后的契约讨论里，避免纯函数层被 ROS 细节污染。
