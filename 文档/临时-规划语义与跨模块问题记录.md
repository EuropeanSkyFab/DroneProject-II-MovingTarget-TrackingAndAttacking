## 代码事实

负责人说的“position 模式、飞控会修正”和代码里的行为不矛盾，但要说清是哪一层：

- 中枢 HOVER 分支每帧取 `my_state` 的当前位置，加队友避让，再发 setpoint。没有保存“按下 HOVER 时的原点”。
  证据：`main:src/center_node_pkg/center_node_pkg/center_node.py:490-528`。
- 算法包 HOVER 分支每帧返回己方当前位置，`reason=hover_hold`。
  证据：`src/algorithm_pkg/algorithm_pkg/plan_policy.py:96`。
- 中枢 HOVER 分支不读 `latest_plan_targets`，所以算法发的 HOVER 点不参与实际悬停控制。
- 飞控修正的是“当前 setpoint”。现在 setpoint 每 50 ms 跟着飞机当前位置走，所以没有“回到原点”的误差。

### 命名问题

`latest_plan_targets` 不是 ROS 话题名，也不是消息名。它是中枢节点里的一个 Python 字典：`{drone_id: PoseStamped}`。

算法发的是 `/planning/target_pose` 的 JSON；中枢 `plan_callback` 收到后已经把它存进 `self.latest_plan_targets[drone_id]`。缺的不是“接收”，是 HOVER 分支不去读这个字典。

所以改名、改话题名都不解决问题。要改的是 HOVER 分支的代码路径：优先读 `latest_plan_targets[drone_id]`，没有规划点再回退到当前位置。

结论：改固定锚点，只改算法不够；中枢也要改成读这个锚点。

### W-08 视觉目标坐标：文档说绝对三维，代码是地面平面投影

文档的写法：

- `main:文档/课题二内部接口规范.md:52-67`：接口 A 要求“视觉节点输出敌方/靶机的绝对三维坐标”，`frame_id=world`。
- `main:文档/课题二内部接口规范.md:177-180`：全系统内部使用 ENU，飞控桥接负责转 NED。
- 接口 A 的示例是 `position: {x: 10.5, y: 20.0, z: 5.0}`，看起来是空中目标。

代码的实际做法：

- `main:src/vision_pkg/vision_pkg/geo_utils.py:74-108`：像素射线与平面 `z=ground_z` 求交，返回交点。
- `main:src/vision_pkg/vision_pkg/vision_node.py:57`：`ground_z` 默认 `0.0`；`:208-214` 把它传给 `pixel_to_world`。
- `main:src/vision_pkg/launch/vision_node.launch.py` 没有覆盖 `ground_z`，所以默认就是地面。
- `main:src/center_node_pkg/center_node_pkg/center_node.py:387-389`：`vision_callback` 丢弃 `z < MIN_ALT=3.0` 的目标。
- `main:文档/进度报告.md:237`：记录过“视觉计算出的贴地异常数据（z=0.0）”被中枢拦截丢弃。

结论：

- 坐标系是绝对的，**深度是假设的**。代码假设目标在 `z=ground_z` 平面上，不是真正测出三维位置。
- 目标是空中靶机时，地面投影的 `x/y` 是视线与地面的交点，不是目标真实位置；`z` 默认是 0。
- 默认参数下，视觉输出 `z=0`，中枢直接丢弃；所以默认视觉目标进不了规划。
- 把 `ground_z` 设成目标高度（比如 5 m）只能修正固定高度目标；目标爬升/下降时仍然错。
- 算法包拿到的是三维点，它无法判断这是地面投影；拦截/跟踪会按错误的三维位置算。

待确认：

1. 目标在地面还是空中？如果是地面目标，中枢的 `z≥3` 门需要改；如果是空中目标，`ground_z` 不够。
2. 是否允许假设目标固定高度？如果允许，`ground_z` 写进 launch，并在接口文档里写明。
3. 要真三维，需要深度相机、双目、已知目标尺寸或运动视差；当前代码没有。
4. 接口文档的“绝对三维”需要补上“平面假设”，或者改成“地面投影点”。

### 视觉输出字段与失败模式

视觉只发一个 `PoseStamped`：

- `header.stamp`、`header.frame_id="world"`
- `pose.position.x/y/z`
- `pose.orientation.w=1.0`，其余姿态分量默认 0

没有速度，没有距离字段，没有置信度，没有“深度是否有效”的标志。算法侧的速度是 `predict_target` 从多帧位置估出来的，不是视觉直接给的。

失败模式只有三种：

- 没检测到目标：不发。
- 内参无效：不发。
- 射线与平面平行或朝上：`pixel_to_world` 返回 `None`，不发。

正常情况一定会发一个“射线与 `z=ground_z` 平面的交点”，不会说“距离不可用”。所以空中目标会得到一个看起来合理、实际错误的坐标。

例子：无人机在 `(0,0,10)`，目标在 `(30,10,5)`，`ground_z=0`。视线从 `(0,0,10)` 穿过目标，继续到 `z=0`，交点是 `(60,20,0)`，不是 `(30,10,5)`。中枢按 `z<3` 丢弃；如果放行，算法会按这个错误点算距离和拦截。

方向对不等于够用：

- 投影点和目标共线，方位对；但距离、速度、`t_go`、`min_distance`、TRACK 的环绕距离都错。
- `INTERCEPT` 用假位置和假速度解方程，拦截点可能不在正确方向；共线只保证当前视线。
- 默认 `z=0` 被中枢丢弃时，算法拿到的是“没目标”，不是“错目标”；一旦放行或改 `ground_z`，才会拿到错点。

接口缺一个“深度无效/平面假设”的标志。算法无法从 `PoseStamped` 分辨真三维点和地面投影点。

接口建议：

- 先定目标类型：地面目标还是空中目标。
- 空中目标：给 `depth_valid`/协方差，或者“方位 + 距离”；不要给假距离。
- 地面目标：改中枢的 `z<3` 门，文档写明“地面平面假设”。

### 责任划分与自身定位

不是单一的 `vision_pkg` 问题，至少四方：

- 视觉：单目没有深度，选了“地面平面”假设；对地面目标合理，对空中目标不成立。
- 接口文档：写“绝对三维”，没写平面假设；示例又给了 `z=5` 的空中目标。
- 中枢：`z<3` 直接丢弃，连地面目标的 `z=0` 也进不来。
- 算法：按接口假设输入是真三维点；它没有能力判断这是地面投影。

自身定位不是问题：

- 规划包不读 IMU。`/drone_<id>/state` 来自桥接的 `position_velocity_ned`，是 PX4 融合后的局部位置估计；纯惯性会漂，PX4 还会融合 GPS、气压、光流等，仓库没有实现惯导。
- 桥接把 PX4 局部 NED 加 Gazebo 偏移转成共享 ENU。这个“世界系”是共享局部坐标，不是经纬度绝对坐标。
- 所以己方坐标是知道的，有估计误差；缺的是目标的距离，不是己方的坐标。

### W-09 规划与中枢的模式切换不同步

两边都订阅 `/strategy/cmd`，但状态门只在中心：

- 规划 `algorithm_node._on_strategy`：只校验 JSON、`drone_id`、动作枚举；通过就改 `_modes`。
- 中枢 `strategy_callback`：有 GROUND 状态门；地面时只接受 TAKEOFF，空中时拒绝重复 TAKEOFF。
- 中心拒绝时不会通知规划；规划已经切了模式。

典型场景：飞机在地面，课题三发 `TRACK`。中心拒绝，规划已经进入 TRACK。下一帧规划发 TRACK 点，中心模式仍是 GROUND，点被忽略。日志两边不一致。

需要确认：中心把“拒绝原因/当前模式”反馈给规划，或者规划也维护同样的状态门。不要只靠两边各自解析同一条指令。

### W-09 更新（2026-11-22 主分支）

- `RESUME_PATROL` 保持原态并告警。

### W-10 拦截只验最早根

`solve_intercept` 先在所有正根里取 `min(candidates)`，再用这个 `t_go` 算拦截点。之后才做 `_turn_infeasible` 判定。

问题：如果最早根转弯半径不够，代码直接退尾随点，不会再试后面的根。后面那个根可能转弯更缓、动力学可达，但代码不会看。

影响：`INTERCEPT` 传了己方速度时，可能把“本可拦截”判成“不可达”。现在没有用例覆盖这个组合；情景 4 的测试没传己方速度，所以没触发。

改进方向（未实施）：遍历所有候选根，逐个做可行性判定，取最早可行根；仍然没有可行根才退尾随点。

## 改法草案（未实施）

### 1. 算法侧：固定锚点

- HOVER 进入时，第一帧拿到有效己方位置，就存为 `anchor`，按 `drone_id` 分开存。
- 之后每帧发 `anchor`，不再用当前位置覆盖。
- 己方状态无效时，本帧不发点，`reason=own_invalid`；等第一帧有效位置再捕获锚点。
- 锚点也要过包线检查：`|x|、|y| ≤ max_xy`，`min_alt ≤ z ≤ max_alt`。越界不发点。
- 动作切出 HOVER 时清掉锚点；下次进入 HOVER 重新捕获。是否在 TAKEOFF/RETURN 后清，待确认。
- 锚点的 z 用捕获时的 z，还是抬到 `safe_alt=5.0`，待 W-04 确认。
- 锚点状态不能放在 `plan_policy.plan()` 里。它是纯函数，没有每机状态。锚点应放在 `DroneRuntime` 或 `DegradeFSM`，或作为参数传进 P2。放哪里待定。

### 2. 时间戳不能跟着锚点冻结

固定锚点后，点不变，但 `stamp` 仍要用当前己方状态时刻，不能用锚点捕获时刻。

原因：中枢 `max_plan_delay=0.8 s` 看 JSON 的 `stamp`。如果 `stamp` 冻结在捕获时刻，0.8 s 后中枢会丢弃所有 HOVER 消息，2 s 后清掉旧点，悬停就断了。

### 3. 中枢侧：读锚点

- HOVER 分支优先用 `latest_plan_targets[drone_id]`；没有可用规划点时，回退到当前位置。
- 中枢的队友避让会改目标点。固定锚点和避让冲突时谁优先，待确认。
- 如果中枢不改，W-01 只改算法不会有效果。

### 4. 测试草案

- 锚点捕获：第一帧 HOVER，`own=(10,20,5)`，`point=(10,20,5)`。
- 抗漂移：第二帧 `own=(12,20,5)`，`point` 仍是 `(10,20,5)`，不是 `(12,20,5)`。
- 时间戳：点不变，`source_stamp` 仍随当前己方状态更新，不能冻结。
- 切模式：HOVER 切 TRACK 再切回 HOVER，锚点重新捕获。
- 己方无效：HOVER 进入时没有己方位置，本帧不发点；第一帧有效位置到来后再捕获。

现有 `test/scenario/test_scenario_behavior.py` 情景 1 断言的是旧语义。改实现时必须改这条断言，不能为了让它过而放宽。
