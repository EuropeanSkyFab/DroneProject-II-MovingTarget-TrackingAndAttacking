# 课题二内部数据接口规范 (V2.0版)

> **给所有模块开发 AI 的提示**： 
> 本系统基于 ROS 2。请严格按照以下定义的话题名（Topic）和消息类型（Message Type）编写代码。 
> 严禁擅自修改接口名称或类型。如果你的模块需要输入，请订阅对应话题；如果需要输出，请发布到对应话题。 
> 课题二使用 uXRCE-DDS 通信方案，请勿使用 MAVROS。

## 1. 系统数据流向拓扑图

本系统采用严格域隔离与多播架构。关键数据源（如视觉、飞控位姿）会同时分发给需要它的模块。

```text
【外部课题一】 ➔ `topic1_adapter` ➔ `/external/target_detected` ➔ 【规划模块】 ➔ `/planning/target_pose` ➔ 【系统集成 (中枢)】 ➔ `/drone_<id>/fmu/in/trajectory_setpoint` ➔ 【飞控 DDS 桥接】 ➔ 【PX4 飞控】

【视觉模块】 ➔ `/vision/target_pose` 
  ├─ (订阅) ➔ 【系统集成 (中枢)】（用于末端锁定、阵型分配与云台超前瞄准）
  └─ (订阅) ➔ 【规划模块】（用于轨迹预测与拦截点计算）

【飞控 DDS 桥接】 ➔ `/drone_<id>/state` ➔ (订阅) ➔ 【系统集成 (中枢)】（用于获取己方无人机当前真实坐标）

【系统集成 (中枢)】 ➔ `/fleet/state` ➔ 【外部课题三】（用于多机态势显示）
```


## 2. 核心接口与数据域定义

### 2.1 目标状态域（Target Domain - 敌方/靶机）

#### 接口 A：视觉高精度目标位姿
- **发送方**：视觉节点
- **接收方**：系统集成节点、规划节点
- **Topic 名称**：`/vision/target_pose`
- **消息类型**：`geometry_msgs/msg/PoseStamped`
- **消息格式示例**：
```text
header:
  stamp: {sec: 123456, nanosec: 789}  # 必须填充真实时间戳
  frame_id: "world"                   # 必须为 world (全局 ENU)
pose:
  position: {x: 10.5, y: 20.0, z: 5.0}
  orientation: {x: 0.0, y: 0.0, z: 0.0, w: 1.0} # 目标朝向（若未知填默认四元数）
```
- **业务约定**：视觉节点输出的是**敌方/靶机的绝对三维坐标**。**视觉模块绝不负责计算己方无人机的拦截点或偏移量**，只充当系统的“眼睛”。目标丢失时停止发送。

#### 接口 B：外部宏观引导
- **发送方**：`topic1_adapter`
- **接收方**：规划节点
- **Topic 名称**：`/external/target_detected`
- **消息类型**：`geometry_msgs/msg/PoseStamped`（暂定，后续若有更复杂的识别结果可扩展）

#### 接口 C：规划拦截目标点
- **发送方**：规划节点（C++）
- **接收方**：系统集成节点
- **Topic 名称**：`/planning/target_pose`
- **消息类型**：`geometry_msgs/msg/PoseStamped`
- **坐标系**：`header.frame_id` 必须填 `"world"`（全局 ENU）
- **业务约定**：规划模块结合外部数据和视觉历史数据，输出**己方无人机应前往的拦截坐标**。若视觉丢失，此话题作为中枢进行“重捕获”的引导源。


### 2.2 己方状态域（Ego Domain - 我方无人机）

#### 接口 D：本体位姿回传
- **发送方**：飞控 DDS 桥接节点
- **接收方**：系统集成节点
- **Topic 名称**：`/drone_<id>/state` （例如：`/drone_1/state`）
- **消息类型**：`nav_msgs/msg/Odometry`
- **消息格式示例**：
```text
header:
  frame_id: "world"
  stamp: {sec: 123, nanosec: 456}
child_frame_id: "drone_1_base_link"  # 必须标明身份
pose: {position: {x, y, z}, orientation: {x, y, z, w}}
twist: {linear: {x, y, z}, angular: {x, y, z}} # 包含自身的速度
```
- **业务约定**：中枢节点依赖此数据计算与目标的相对距离，并用于多机之间的空间防撞。

#### 接口 E：态势广播
- **发送方**：系统集成节点
- **接收方**：外部课题三
- **Topic 名称**：`/fleet/state` （或者继续用 `/drone_<id>/state`）
- **消息类型**：`nav_msgs/msg/Odometry`
- **业务约定**：中枢节点将己方集群的所有位姿统一打包或分包，发给课题三进行态势显示。


### 2.3 控制输出域（Control Domain）

#### 接口 F：飞行控制指令（集群版）
- **发送方**：系统集成节点
- **接收方**：飞控 DDS 桥接节点
- **Topic 名称**：`/drone_<id>/fmu/in/trajectory_setpoint`
- **消息类型**：`px4_msgs/msg/TrajectorySetpoint`
- **消息格式示例**：
```text
timestamp: 123456789
position: [y_enu, x_enu, -z_enu] # 中枢发出的是加过阵型偏移的个体目标点(ENU)，底层转NED
velocity: [nan, nan, nan]
```
- **业务约定**：中枢节点根据集群分配算法，为每一架己方无人机计算带偏移量的“个体目标点”，再分别下发给各自的飞控底层。

#### 接口 G：云台协同指令
- **发送方**：系统集成节点
- **接收方**：飞控 DDS 桥接节点
- **Topic 名称**：`/drone_<id>/fmu/in/gimbal_setpoint`
- **消息类型**：`px4_msgs/msg/GimbalManagerSetPitchYaw`（暂定）
- **业务约定**：中枢根据视觉目标的像素偏差，在 VISION 模式下计算云台偏转角并下发，实现“云台与机体协同”。


## 3. 坐标系规范（全系统铁律）
- **内部算法坐标系**：除飞控 DDS 节点外，全系统统一使用 ROS 标准的 **ENU 坐标系**（东-北-天，Z轴向上为正，单位：米）。
- **飞控坐标系**：PX4 底层使用 NED（北-东-地）。
- **坐标转换职责**：由底层的飞控 DDS 桥接节点统一负责将中枢发出的 ENU 坐标转换为 NED。其他模块严禁加坐标系转换逻辑。


## 4. 自主预测与重捕获职责边界
1. **轨迹级预测（规划模块）**：利用视觉高频坐标，推算目标“拦截提前点”，以 `/planning/target_pose` 发送。
2. **瞄准级预测（中枢模块）**：在 VISION 模式，根据视觉坐标与历史坐标计算移动趋势，在控制云台时加入提前量。
3. **重捕获逻辑（中枢模块）**：视觉超时切断后，中枢切入 GUIDANCE 模式，使用规划给出的预测坐标飞行搜索；若重捕获成功，立刻切回 VISION 模式。


## 5. 系统时间同步与延迟过滤规范（铁律）

在真实物理系统中，视觉计算、网络传输、C++ 规划都会产生毫秒级延迟。为了防止无人机追踪“过去的残影”，全系统必须严格遵守以下时间规范：

### 5.1 统一时钟源（当前阶段：禁用 Sim Time）
- **WSL 环境限制说明**：经过近期测试发现，在当前 WSL（Windows Subsystem for Linux）仿真环境下，若强制开启 `use_sim_time:=true`，会导致 ROS 2 节点的底层定时器发生“假死”（表现为能接收消息但无法下发）。
- **当前规定**：为保证系统顺利跑通，目前阶段**全系统统一禁用 `use_sim_time`**，所有节点（视觉、规划、中枢、飞控桥接）均使用电脑的真实系统时间（即不传入该参数）。
- *(注：待后续项目迁移至原生 Ubuntu 环境或实机验证时，再统一启用 `use_sim_time` 对齐 Gazebo 时钟。)*

### 5.2 时间戳的源头标记（Header.stamp）
- 所有包含 `header` 的消息（如 `PoseStamped`, `Odometry`），其 `header.stamp` **必须由数据的“生产者”填充**。
- 例如：视觉节点在算出 3D 坐标的瞬间，必须打下当前时间戳；规划节点在算出拦截点的瞬间，必须打下时间戳。中枢节点绝对不允许去“伪造”或“覆盖”上游发来的时间戳。
- **标准写法**：`msg.header.stamp = self.get_clock().now().to_msg()`

### 5.3 过期数据过滤（延迟阈值）
- 系统集成（中枢）节点在接收数据时，必须计算数据延迟：`延迟 = 当前系统时间 - msg.header.stamp`。
- **视觉数据**：若延迟 > `0.2` 秒（200ms），直接丢弃该帧，防止控制滞后。（阈值可能视实机情况调整）
- **规划数据**：若延迟 > `0.5` 秒，直接丢弃。（阈值可能视实机情况调整）
- 发生丢弃时，中枢节点应打印警告日志，并可能触发降级策略（如悬停等待最新数据，或切回上一级引导）。
